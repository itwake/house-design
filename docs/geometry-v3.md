# V3 住宅几何审计与建模依据

审计日期：2026-09-07。对象：荟雅苑 104.83㎡、28F，三房两卫恢复方案。本文件记录新 Blender 场景与 Three.js 网页共用的几何修正；不将参考图推算数值当作现场实测。

## 使用哪份数据

- `models/design-data.json`：V3 的房间、墙线、门窗及家具平面占位，共用一套厘米坐标。
- `models/blender-overrides.json`：完整 V3 开口清单及旧家具的修正说明。`openings` 是替换清单，不应叠加到旧开口上。
- `models/model-data.json`、`models/Home.xml`、`models/huiyayuan-104-calibrated.sh3d`：保留的 V2.3 归档，不得与 V3 的新墙线混合使用。
- `assets/current-ziroom-plan.jpg`：目标房源现状尺寸图，优先用于总宽、总长和已标注尺寸。
- `assets/original-plan.webp`：同户型参考图，辅助判断门厅、凹口、窗和阳台；与目标尺寸图的不同处不能无说明地相互替换。

## 坐标和单位

源数据 x 向东、y 向南，图上方为北；单位厘米。Blender 采用米和 Z 向上，建议映射为 `(X,Y,Z)=(x/100,-y/100,z/100)`。因此源数据平面角度 `angle` 转 Blender Z 旋转应取负号。导出 GLB 时交给 Blender 的 glTF 导出器处理其 Y-up 坐标约定，网页不要再次交换轴或额外乘 100。

`design-data.json` 的家具 `x,y` 是全局平面包围盒左上角，`w,d` 是全局 x、y 跨度。旧 `Home.xml` 的家具 `x,y` 是中心点，`width,depth` 是旋转前局部宽深。二者不能原样互换。XML 的 `height` 是竖向高度，底面为 `elevation`；若用 Blender 中心立方体创建家具，中心 Z 应为 `elevation + height/2`。

## B门厅与C凹口的纠正

两张参考户型图均显示：次卧B向东南延伸出小门厅，小卧C的东北角为凹口，B的门在门厅东侧朝向公共过道。

旧模型把B/C都简化成矩形，B门却放在两房之间的水平墙上，段为 `x=228..313,y=328`。门南侧约490 mm面向C房、120 mm面向墙端，仅约360 mm接到公共过道。这是房间连通关系错误，旧“门洞已与分墙脱开”的说明不足以证明门可用。

V3按参考图恢复如下厘米坐标：

```text
B房：[(12,12),(313,12),(313,422),(223,422),(223,322),(12,322)]
C房：[(12,334),(211,334),(211,434),(313,434),(313,620),(12,620)]
B/C东侧墙中心：x=319
B门：x=319, y=335.5..420.5，暂定850 mm，向B内开
C门：x=319, y=457.5..542.5，暂定850 mm，向C内开
北走廊：x=325..410，净850 mm
主卧门：x=327.5..407.5,y=328，暂定800 mm
```

主卧旧900 mm门东端与湿区墙端相交，V3暂缩至800 mm并居中于走廊，这是为当前推算几何作的C级门洞调整。B/C新凹口、门位和850 mm走廊都须复尺后确认，不构成可直接拆建的结构设计。

床、主卧与次卧衣柜、电视、沙发、餐桌和主要湿区设备继续以数据中的占位为设计基础。床头的高度与窗台关系、抽屉拉出/衣柜门开启、门扇开启方向属于深化项目；静态投影不相交不能代替可用性证明。

客厅电视继续放双卫南侧实墙，西窗前600 mm范围保持净空。主卧与客卫命名是方案用途，两卫均从公共过道进入，不是主卧套内独卫。

## 门窗证据与保留未知

两张图可直接支持北侧两卧窗、小卧西窗与客厅西窗的存在。旧模型仅有这四个窗，并漏掉同户型原图东墙的两卫窄窗。

V3补入：主卫东窗 `x=681,y=365..435` cm；客卫东窗 `x=681,y=530..590` cm。两窗暂用窗台150 cm、窗高80 cm，全部标C级。主卫目标尺寸图同侧可见开口痕迹；客卫存在主要由同户型图支持，目标房源须复核。不能把暂定的700/600 mm宽当作已测尺寸。

阳台参考图有外侧边界，但现状封窗形式、北/东两侧开口、栏杆高度以及厨房外窗资料不足，本次没有虚构新增开口。若新画面保留这些面的封闭占位，不得据此推断阳台“没有采光”，也不能把任意整面落地窗渲染成已经证实的事实。

两卫门当前暂定750 mm、北走廊850 mm。旧说明要求外开/移门，但移门收纳段及相邻门冲突并未经过现场验证。本版按关闭状态展示门，实际合页、折叠/外开或移门方案需复尺深化。

## 旧图为何不可靠与新相机要求

旧 `Home.xml` 主卧、次卧等机位采用 `z=240 cm,pitch=1.50 rad,FOV=2.10 rad`，约86°向下、120°视角，是强俯视相机。旧 `assets/renders/master.png` 中可见的是床的俯视投影；床基础高22 cm、床垫高23 cm，床本身并未竖起。

随后生成的AI主卧图把地面当作后墙、床头柜当作小窗，并补出立视床和天花。它虽有漂亮材质，却不保持真实相机和窗位。`assets/concepts/`及更早`assets/design/`不能作为V3建模依据。

新Blender画面应直接由共享几何渲染。站立室内视角建议眼高约1.55 m、24–35 mm镜头；极小空间用明确标注的去顶/斜俯视。所有灯光、窗外背景和软装细节仍是设计表达，不能反向证明未知门窗。

## SH3D与GLB

现有SH3D是ZIP容器，含Home.xml、归一化box/cylinder/door/glass-opening OBJ、MTL和一张木门贴图；不含完整房屋GLB。OBJ大多是基础盒体，缺少精细家具网格和适合展示的材料系统。

从这些参数可以可靠重建尺寸和占位，也可经完整房屋网格导出再转GLB，但“解压OBJ就得到完整房屋”不成立：墙开口、房间地板、组件变换都来自Home.xml场景逻辑。直接转旧SH3D只会保留旧门厅和朝向错误。V3应按纠正后的design-data在Blender构建真实门窗洞、家具网格和材质，再导出同一场景GLB供Three.js显示。

已校核新C桌、椅、柜和保留日床投影在C多边形内且相互无重叠；B/C门两侧分别连通对应房间和公共过道；两卫窗位于东侧墙线上；主卧门避开走廊端墙。下游还需验证GLB导出后的单位/轴向和开口、房间点击映射、实际渲染画面。
